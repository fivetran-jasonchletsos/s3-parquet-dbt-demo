dbt transforms parquet in S3

Three engines, one set of dbt models, five parquet files read in place from a bucket. No copy or load step into a warehouse.

01The question

Can dbt transform parquet files stored in S3?

Asked by Andy Ellman. The doubt is reasonable: dbt is usually shown transforming tables that already live inside a warehouse, and "files in a bucket" sounds like an ingestion problem.

Yes. dbt does not move data; it compiles SQL and hands it to an engine. Any engine that can read parquet in S3 can be the dbt backend. Proven here live on DuckDB and Snowflake against the same bucket, with a Databricks project built and parse-validated. Identical models, identical results.
02How it works

The files are the source, the engine is the compute

Five parquet files sit at s3://jason-chletsos-parquet-dbt-demo/raw/ (us-east-1): 500 customers, 50 products, 5,000 orders of trading-card storefront sample data. Each engine reads those files where they sit; dbt builds the same three staging views and one fact table on top.

"In place" means exactly that: no COPY INTO, no staging load, no warehouse-resident copy of the raw data. Snowflake's external tables, Databricks' read_files, and DuckDB's httpfs all scan the bucket objects at query time. To be precise about outputs: the staging views are stored SQL, and fct_daily_revenue materializes as a native table in each engine (DuckDB file, Snowflake table, Delta on Databricks) — the raw data is never loaded, the curated aggregate is. Writing model outputs back to S3 as parquet or Iceberg is the follow-on pattern, not shown here. The Databricks project is built and parse-validated; the live run is pending a workspace with a Unity Catalog external location. Its IAM role is already provisioned in Terraform.

04Runbooks

Reproduce it per engine

Each dbt project carries its own profiles.yml and runs with --profiles-dir ., so nothing touches ~/.dbt. Full step-by-step runbooks live in each project's README in the repo.

DuckDB

httpfs + credential_chain secret

The zero-infrastructure proof. Default target reads the checked-in local files; the s3 target reads the bucket directly, picking up AWS SSO credentials automatically.

cd dbt_duckdb
python3 -m dbt.cli.main build --profiles-dir .              # local files
python3 -m dbt.cli.main build --profiles-dir . --target s3  # same files in the bucket
dbt_duckdb/README.md

Snowflake

storage integration + dbt_external_tables

One-time setup creates the storage integration, stage, and grants (setup/snowflake_setup.sql), with the standard two-step trust handshake: DESC INTEGRATION returns Snowflake's IAM user and external ID, which get stamped into the IAM role trust policy on the AWS side. Then:

cd dbt_snowflake
python3 -m dbt.cli.main deps --profiles-dir .
python3 -m dbt.cli.main run-operation stage_external_sources --profiles-dir .
python3 -m dbt.cli.main build --profiles-dir .
dbt_snowflake/README.md

Databricks

read_files over s3:// + Unity Catalog

Staging views call read_files(..., format => 'parquet') against the raw S3 paths; only fct_daily_revenue is persisted, as a Delta table. Needs a Unity Catalog storage credential and external location (documented in setup/databricks_setup.md); the IAM role it assumes is already provisioned.

cd dbt_databricks
python3 -m dbt.cli.main parse --profiles-dir .   # offline validation
python3 -m dbt.cli.main run --profiles-dir .     # once a workspace is wired
python3 -m dbt.cli.main test --profiles-dir .
dbt_databricks/README.md

05Field notes

Two things that actually broke

Both hit during the live Snowflake run, both fixed, both worth knowing before a customer conversation.

Cross-cloud external tables

auto_refresh must be false when Snowflake is not on AWS

The sales_eng_demo Snowflake account is not hosted on AWS, and external-table auto-refresh depends on cloud-native event notifications that do not cross clouds. Snowflake defaults auto_refresh to true and errors on creation. Fix: set auto_refresh = false explicitly in the external table definition and refresh on demand.

Timestamp semantics

TIMESTAMP_TZ re-stamps parquet UTC with the session timezone

Typing the parquet's UTC timestamp column as TIMESTAMP_TZ made Snowflake reinterpret the UTC wall-clock in the session timezone (America/Los_Angeles), silently shifting every instant by 7 to 8 hours — enough to move orders across date boundaries and break parity on the daily grain. Fix: type it TIMESTAMP_NTZ (naive UTC) and take a plain date cast. After that, the daily grain matches across all engines exactly.

06Scale and limits

What 5,550 rows does and does not prove

The runs above prove the mechanism, not the economics. External tables and read_files carry no micro-partitions, clustering, or table statistics, so every query rescans the files — pruning is limited to what the parquet footers and the S3 path layout provide. At this volume that is invisible; at production volume it is the bill.

The mitigations, in order: partition the S3 paths (by date, typically) so engines can skip whole prefixes; move to Iceberg — which is what Fivetran MDLS lands — for file-level statistics, snapshots, and compaction; and past meaningful volume, materialize hot marts as native tables, which this demo already does for fct_daily_revenue. The pattern fits landing and staging zones best: one raw copy in S3, dbt transforming it in place, native storage reserved for curated aggregates.

Incremental models work unchanged — the engine owns the SQL, so an incremental fct_daily_revenue filtering on order_ts compiles and runs the same way. The one operational caveat is Snowflake's external-table refresh (field note above); with MDLS the Iceberg catalog removes it, because new files surface as new table snapshots.

07The Fivetran angle

Fivetran can own the landing

The generator and upload script in this repo simulate parquet that already lands in S3. In production, Fivetran's Managed Data Lake Service replaces both: connectors write to your S3 bucket as parquet-backed Iceberg tables that Fivetran maintains — initial sync, incremental updates, schema evolution, compaction.

The transform pattern is unchanged. Snowflake and Databricks read the Iceberg tables in place through their catalogs, the dbt staging models point at those tables instead of raw paths, and everything downstream — fct_daily_revenue, the schema tests — is identical. One copy of the data in S3 serves every engine. Details in fivetran/INGESTION.md.

When an SE reaches for this

Point at a lake destination when the customer wants one copy of the data queried by multiple (or future) engines without re-ingesting; when ownership or residency requires the data to live in their bucket, not a vendor's storage; or when the architecture is warehouse-optional and compute should stay swappable. The warehouse destination is still right when one warehouse serves all workloads and its native storage features carry the query load, when the team wants no lake-side moving parts to operate, or when interactive latency on large scans outweighs storage flexibility.

The talk track in one breath: Fivetran lands governed Iceberg in the customer's bucket, and dbt transforms it in place on whatever engine they already pay for. Their data, their account, swappable compute.
